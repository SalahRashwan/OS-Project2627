# Assumptions and open-question register — Nostos Phase 1

This file tracks every decision the statement (`P`), the style guide (`S`), the official test
sheet (`T`), and the rubric (`R`) leave underspecified. Each entry states the recommended
default actually implemented, the reasoning, and whether it still needs instructor
confirmation. None of these are presented as verbatim instructor requirements; they are
this implementation's documented choices, kept easy to change in one place (the cited
module/function) if an instructor gives a different ruling.

| ID | Issue | Decision implemented | Status |
| --- | --- | --- | --- |
| A01 | Scope: is this a Phase-1-only delivery? | Implemented Phase 1 only, per the student's explicit instruction and the `Phase1/` folder naming. Phases 2/3 material was read for context only; nothing from them was coded. | Resolved by explicit user instruction. |
| A02 | P p.20 says a design document is "not mandatory" but recommends validation; P p.38 says "overall design validation... is mandatory before Phase 1." | Both statements are recorded here rather than silently reconciled. `docs/design.md` was produced and is ready for monitor review. No validation meeting has taken place. **This implementation must not be presented as instructor-approved.** | **Unresolved — pending student/instructor action.** |
| A03 | Only one Ithaca may run at a time; no enforcement mechanism is specified, and Phase 1 bans sockets/semaphores/IPC that could enforce it. | No singleton enforcement was added (would require exactly the mechanisms Phase 1 forbids). Only one `ithaca` was ever run during testing. | Unresolved — ask whether runtime enforcement is expected in a later phase. |
| A04 | Voyage ID numbering policy — `voyages.dat` carries no ID column. | IDs are assigned sequentially starting at 1, in file order, during `loadVoyages()` (`src/voyages.c`). IDs are internal only; never written back to the file. | Implemented default. |
| A05 | Exact numeric lexical grammar beyond "numerically valid." | Digit-only decimal tokens (`[0-9]+`), no leading `+`/`-` sign, leading zeros accepted (`0002` == 2). Value must be representable and satisfy the context bound: voyage IDs and BUY/SELL quantities must be `1..INT_MAX`. `strtol` is used with full-token-consumed and `ERANGE` checks (`src/text.c: parseDigitsToLong`). Signs, decimal points, exponents, and any non-digit character are rejected as usage errors, never as `Unknown command`. | Implemented default. |
| A06 | `BUY MAP 2` — is quantity checked in Phase 1? | Table 1 fixes `BUY MAP 1` explicitly, and no product-quantity semantics exist yet. This implementation treats a non-1 quantity paired with the literal token `MAP` (case-insensitive) as a `BUY` usage error, on the theory that the *grammar* for that one product name is fixed, not that Phase 2 funds/inventory are being checked. Any other product name accepts any positive quantity. If an instructor rules quantity is free in Phase 1, this is a single `if` in `src/commands.c: classifyBuySell()`. | Implemented default — explicitly flagged as an interpretation, not a golden rule. |
| A07 | `SELL MAP 1` vs. the later rule that maps cannot be sold. | Accepted at the grammar level like any other `SELL <product> <amount>`; no product-membership or map-specific restriction is applied to `SELL`. Semantic map-trading rules belong to Phase 2. | Implemented default. |
| A08 | Blank / whitespace-only command line. | Silently ignored: no `Command OK`, `Unknown command`, or usage text is printed; the terminal simply reprompts (`$ `). Rationale: a blank line is not one of the eleven commands and is not "unknown" in the sense of a bad verb either — it carries no verb at all. | Implemented default — documented as a UX choice, not an official string. |
| A09 | `LIST nonsense`, `CONNECT elsewhere` — usage error or unknown command? | Recognized first words (`CONNECT`, `LIST`) are treated as a command *family*: any second word / arity mismatch is a usage error, never `Unknown command`. For a bad or missing `LIST` subcommand, both supported usages are printed (`Usage: LIST VOYAGES` then `Usage: LIST MARKET`) since the user has not yet picked a valid subcommand. Once a *valid* subcommand is present but has extra tokens, only that one usage line is printed. Only a first token matching none of the eleven verbs is `Unknown command`. | Implemented default. |
| A10 | Relative file paths (config paths, voyage object paths, `objects/`). | All paths are stored exactly as given; no path is rewritten, normalized, or prefixed. Relative paths are resolved by the kernel's `open()` against the process's current working directory, exactly as an ordinary `open()` call would. The fixture layout under `nostos/` matches the supplied voyage paths (`objects/....png`, lowercase) so that running from `nostos/` as CWD would locate them if a later phase opens them; Phase 1 itself never opens the PNGs. `objects/` is never prefixed a second time. | Implemented default. |
| A11 | Figure 9 shows `>>> THE STARS HAVE BEEN CONSULTED.` after `MAP`. | Not implemented. The explicit Phase 1 rule (P p.15, confirmed by the official test sheet `T`) is that *every* recognized, syntactically valid command — `MAP` included — prints exactly `Command OK` and nothing else. Figure 9 is a later-phase illustration; T p.2's authoritative table lists `MAP` → `Command OK` only. | Resolved by explicit rule precedence. |
| A12 | No `config.dat` files were supplied for `odysseus`/`ithaca`/`island`. | Fixture configs were authored from the statement's documented formats (`nostos/configs/*.dat`) and clearly labeled as self-authored fixtures, not supplied grading data. Sample IPs (`172.16.214.x`) are illustrative, matching the statement's own example octets. Ports reuse the assigned range 8620-8624 across distinct sample IPs (7 endpoints needed, only 5 ports assigned) — documented in `README.md`, never a live deployment. | Implemented default. |
| A13 | Style guide's Annex III / header example shows globals directly in a header; the project rule prefers no mutable globals. | No mutable global variables are defined in any shared header or reusable module. Each entry-point (`Odysseus.c`, `Ithaca.c`, `Island.c`) keeps its own `volatile sig_atomic_t`-free design: signal delivery is handled through a blocked-SIGINT + `signalfd` descriptor read from the normal `poll()`/`read()` control flow, not a global flag inspected asynchronously (see `src/lifecycle.c`). No header declares a mutable global; only `extern` declarations would be used if one were ever unavoidable, and none was needed. | Implemented default. |
| A14 | Hungarian style vs. vendor/system names (`SPHRAGIS_Island.name`, `errno`, `struct pollfd.revents`, etc.). | Style guide naming is applied to every authored identifier. External struct field names, library function names, and system-defined types/macros are preserved exactly as declared by their owning API and are never renamed to satisfy Hungarian notation. | Implemented default. |
| A15 | Authors, group number, IPs, actual hours spent. | Left as explicit pending fields in `docs/report.md`. Group number and teammate names are not established by this handoff and were not invented. Only the confirmed data (student name Salah Ahmed Salaheldin Adly Rashwan, assigned ports 8620-8624, this session's actual test run timestamps) are recorded. | **Unresolved — pending student input before submission.** |
| A16 | No integration documentation for Sphragis beyond `sphragis.h`. | The header and the supplied `.o` were used exactly as provided; only real link/run behavior observed on WSL Ubuntu 24.04 (a genuine GNU/Linux target, see `docs/test-results.md`) was used as evidence. No helper functions or extra linker flags were invented; none were needed to link or run `island`. | Implemented; Montserrat re-verification still pending (see `docs/test-results.md`). |

## Additional decisions not in the original A01-A16 list

| ID | Issue | Decision implemented |
| --- | --- | --- |
| A17 | `ACCEPT <id>` upper bound. | Digit-only token parsed with `strtol`, rejecting `ERANGE`, then bounded to `INT_MAX` (voyage IDs are stored as `int`). A syntactically valid but enormous ID (e.g. `999999999999`) is a usage error (overflow), not `Command OK` with silent truncation, and not `Unknown command`. |
| A18 | Duplicate destination names inside one island's raw `--- ROUTES ---` section. | Rejected at raw-parse time as a malformed configuration (`src/config.c: loadIslandRawRoutes`) — the loader fails cleanly rather than silently keeping only one endpoint per name, as a defensive-parsing choice. All six supplied/authored fixtures have no duplicates, so this never fires against valid input. |
| A19 | Adapter behavior when `SPHRAGIS_filter_island_configuration()` returns a negative error. | The temporary per-call name array is defensively freed (any surviving non-NULL slot is freed once) before propagating the error, because the header does not document whether the library mutates the array on an error return. This is a defensive assumption, not a proven library guarantee — flagged in `docs/audit-handoff.md` for anyone re-testing against a different library build. |
| A20 | Terminal read chunk size / line length limits. | No fixed maximum command-line length is enforced; the line accumulator (`src/text.c: tLineBuffer`) grows geometrically from a small initial capacity. Dynamic input is preferred over arbitrary small limits. |
| A21 | Exit status convention. | `0` for a normal CTRL+C/EOF shutdown after full cleanup; a documented nonzero status (`1` for CLI/argument errors, `2` for any I/O, allocation, or Sphragis-adapter failure, during initialization or at run time, always accompanied by a stderr diagnostic) otherwise. Not an official requirement — chosen for test-harness clarity and documented in `README.md`. |

Every "Unresolved" row above is a genuine open question for the student/instructor, not a
gap in the implementation: the code takes the documented default in each case and is
built so the default can be changed locally without touching unrelated modules.
